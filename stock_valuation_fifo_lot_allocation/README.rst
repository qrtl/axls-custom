For FIFO products tracked by lot/serial number, this module persists one
record every time a stock valuation layer is created, capturing how much
of that layer's value and quantity is charged to each lot.

``stock_valuation_fifo_lot`` already produces the correct per-lot
remaining value on the stock move line, but it only exposes the current
balance. Landed costs, vendor bill price differences and revaluations
leave no per-lot trace, so there is no way to explain how a lot arrived
at its value. This module records the split at the moment the layer is
created, while the information needed to split it is still available, so
that at audit time you can list, group and drill down into exactly why
each lot carries the value it does.

Each allocation row carries an amount and a quantity (in the product
UoM, signed as the layer quantity), so that it fully shadows the per-lot
layer Odoo would create if it valued lots natively:

-  incoming layers: the lot's received quantity (``qty_base``), and the
   value prorated on it;
-  outgoing layers: the quantity and value the FIFO run consumed from
   the lot (the increase of ``qty_consumed`` and ``value_consumed`` on
   the lot's incoming move lines);
-  value-only layers (landed cost, price difference, revaluation): no
   quantity, and the value prorated on the remaining quantity of the
   lots in scope.

The ledger satisfies the following invariants, which the *Check
Integrity* action verifies:

-  per layer, the allocations add up to the layer value;
-  per lot, the allocations add up to the lot's remaining value
   (``stock.move.line.value_remaining``).

Bridge to core lot valuation (18.0+)
------------------------------------

Odoo 18.0 values lots natively (*Valuation by Lot/Serial number* on the
product, with a lot on each stock valuation layer). This module is a
16.0 bridge to that model and is not meant to be migrated as such: at
upgrade, it is replaced by converting each allocation row into a per-lot
valuation layer (lot, quantity = ``allocated_quantity``, value =
``allocated_amount``) in place of the aggregate layer it belongs to.
Opening adjustment rows become value-only per-lot layers. The invariants
above are what make that conversion lossless, and should be checked
before upgrading.

Usage
=====

Go to *Inventory > Reporting > Lot Valuation Allocation*.

The list is grouped by lot/serial number and ordered by actual date.
Each line drills through to the valuation layer it comes from, and the
group totals equal the lot's remaining value and quantity. The pivot
view breaks the allocated amount and quantity down by lot and period.

Health check
------------

Select records in the list and run *Action > Check Integrity* to verify
the invariants over the whole ledger (in the companies currently
selected). The result lists the layers whose allocations do not add up
to their value and the lots whose allocations do not add up to their
remaining value; a per-lot drift of one rounding unit, from rounding
each layer per lot, is tolerated. Run it once the backfill has
completed, as lots still carrying value from layers not yet allocated
are reported otherwise.

Historical layers
-----------------

On installation, a scheduled action backfills the valuation layers that
already exist. It processes them in batches, oldest first, and
deactivates itself once the backlog is drained. Progress is kept in the
``stock_valuation_fifo_lot_allocation.backfill_last_id`` system
parameter; to rebuild the ledger from scratch, delete the allocation
records, reset that parameter and the ``...backfill_balanced`` one, and
reactivate the scheduled action (or run the *Run Lot Allocation
Backfill* server action).

Historical figures cannot be reconstructed exactly: remaining quantities
are a current snapshot rather than an as-of-date value, and past per-lot
FIFO consumption is not recorded per layer. Incoming layers are
backfilled exactly; outgoing and value-only layers are approximated, and
once the backlog is drained a single *Opening allocation adjustment*
record per lot absorbs the value difference, so the invariants hold
exactly and every approximation stays visible in one auditable row.
Adjustment rows carry no quantity.

Forced FIFO lots
----------------

When a *Force FIFO Lot/Serial* is set on an outgoing move line, the
ledger charges the lot whose FIFO balance was consumed, not the lot
physically shipped. This is what keeps the ledger consistent with the
valuation.

Known issues / Roadmap
======================

-  A product-wide revaluation of a lot tracked FIFO product is spread
   over the lots in proportion to their remaining quantity. This is
   consistent with what Odoo does to the valuation layers, but it is a
   quantity weighted spread, not a per-lot judgement; use the lot
   revaluation of ``stock_valuation_fifo_lot`` instead when the value
   belongs to a specific lot.
-  Applying a landed cost to a receipt after the lot has been revalued
   is outside the scope of ``stock_valuation_fifo_lot``, and remains so
   here.
-  Not to be migrated to 18.0: see *Bridge to core lot valuation* in the
   description for the conversion that replaces it.
