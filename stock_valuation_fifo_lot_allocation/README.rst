For FIFO products tracked by lot/serial number, this module persists one
record every time a stock valuation layer is created, capturing how much
of that layer's value and quantity is charged to each lot.

``stock_valuation_fifo_lot`` already produces the correct per-lot
remaining value on the stock move line, but it only exposes the current
balance. Landed costs, vendor bill price differences and revaluations
leave no per-lot trace, so there is no way to explain how a lot arrived
at its value. This module records the split at the moment the layer is
created, while the information needed to split it is still available, so
that at audit time you can list, group and drill down into exactly why
each lot carries the value it does.

Each allocation row carries an amount and a quantity (in the product
UoM, signed as the layer quantity):

-  incoming layers: the lot's received quantity (``qty_base``), and the
   value prorated on it;
-  outgoing layers: the quantity and value the FIFO run consumed from
   the lot (the increase of ``qty_consumed`` and ``value_consumed`` on
   the lot's incoming move lines);
-  value-only layers (landed cost, price difference, revaluation): no
   quantity, and the value prorated on the remaining quantity of the
   lots in scope: those of the layer's move (landed cost), of the move
   of the layer it corrects (price difference), or of the whole product
   (product revaluation).

The ledger satisfies the following invariants:

-  per layer, the allocations add up to the layer value;
-  per lot, the allocations add up to the lot's remaining value
   (``stock.move.line.value_remaining``).

Usage
=====

Go to *Inventory > Reporting > Lot Valuation Allocation*.

The list is grouped by lot/serial number and ordered by actual date.
Each line drills through to the valuation layer it comes from, and the
group totals equal the lot's remaining value and quantity. The pivot
view breaks the allocated amount and quantity down by lot and period.

Historical layers
-----------------

On installation, a scheduled action backfills the valuation layers that
already exist. It processes one batch per run, newest first,
re-triggering itself until the backlog is drained, and then idles,
setting the system parameter
``stock_valuation_fifo_lot_allocation.backfill_before_id`` to ``-1``.
Layers that already have allocations are skipped, so deleting that
parameter fills in whatever is missing on the next run; to rebuild the
ledger from scratch, delete the allocation records and the parameter.

Past FIFO runs are not recorded per layer, so the backfill reconstructs
them:

-  incoming layers: as above, exact;
-  outgoing layers: a lot received once is charged its delivered
   quantity at the rate of its receipt line
   (``value_consumed / qty_consumed``), and the lots received several
   times (e.g. through a lot revaluation) share the rest of the layer
   value, prorated on their quantity;
-  value-only layers: prorated on what the lots held when the layer was
   posted, that is their current remaining quantity plus what later
   deliveries took from them. A lot received several times keeps its
   current remaining quantity, as which receipt the later deliveries
   drew on is not known.

This is exact as long as no value (landed cost, price difference,
revaluation) landed on a receipt after its first delivery, and, for a
value-only layer or a delivery of several such lots, the lots were
received only once; other cases are approximated. Once the backlog is
drained, a single *Opening allocation adjustment* record per lot absorbs
whatever difference is left, so the invariants hold exactly and every
approximation stays visible in one auditable row. Adjustment rows carry
no quantity.

Forced FIFO lots
----------------

When a *Force FIFO Lot/Serial* is set on an outgoing move line, the
ledger charges the lot whose FIFO balance was consumed, not the lot
physically shipped. This is what keeps the ledger consistent with the
valuation.
